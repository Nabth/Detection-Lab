# Gap Analysis: Известные ограничения и слепые зоны

Этот документ описывает архитектурные особенности лабораторного стенда, которые проявились в ходе проектирования и боевого тестирования.

## 1. Разделение ответственности L3/L4 и L7 (TLS)

**Симптом:** Suricata IDS не видит полезную нагрузку веб-атак (SQLi, XSS) и не генерирует по ним алерты.
**Причина:** Трафик на порт 443 зашифрован (TLS). Suricata работает в пассивном режиме (sniffing) и не имеет доступа к расшифрованному пейлоаду (нет MITM-прокси).
**Вердикт:** Это by design. Suricata отвечает за L3/L4 (флуды, сканы, аномалии TCP), а L7 (веб-атаки) инспектирует Nginx + Coraza WAF, который терминирует TLS. Атаки L7 видны только в WAF и логах Nginx.

## 2. Slowloris и HTTP/2 (Архитектурный Gap)

**Симптом:** При попытке провести атаку Slowloris (HTTP/1.1) Nginx отдает код `400 Bad Request`, и в `error.log` не появляется записи `client timed out`.
**Причина:** Nginx в Docker-контейнере настроен на HTTPS с поддержкой HTTP/2. Когда атакующий отправляет неполный HTTP/1.1 заголовок, парсер Nginx (или WAF Coraza) мгновенно классифицирует его как невалидный и сбрасывает соединение, не дожидаясь таймаута `client_header_timeout`.
**Вердикт:** Корректное поведение защиты. Атака отбивается на уровне HTTP-парсера. Правило Wazuh `100302` написано и протестировано, но в данной архитектуре не генерирует алерт, так как Nginx не пишет таймаут в лог.

## 3. Race Condition: L3/L4 DDoS vs L7 HTTP Flood

**Симптом:** При запуске HTTP Flood (60 параллельных запросов) в Wazuh срабатывает правило ACK Flood (`100205`), а правило HTTP Flood (`100300` на основе 429 кода Nginx) не генерируется.
**Причина:** Suricata на уровне L3 видит всплеск TCP-пакетов и мгновенно генерирует алерт. Wazuh запускает Active Response и банит IP атакующего (`iptables DROP`). Nginx (L7) не успевает получить оставшиеся пакеты, чтобы накопить `limit_req` и выдать 429.
**Вердикт:** Доказывает эффективность эшелонированной защиты. Сетевой уровень отбивает атаку быстрее, чем прикладной.

## 4. WAF Evasion: SQLMap и Paranoia Level 1

**Симптом:** WAF блокирует классические инъекции (SQLi, XSS), но инструмент `sqlmap` с tamper-скриптами (обфускация) может обойти защиту.
**Причина:** OWASP CRS (Paranoia Level 1) ориентирован на блокировку очевидных сигнатур. Обфускация запросов с помощью комментариев (`/**/`), `between` и `randomcase` требует более высокого уровня паранойи (PL2 или PL3).
**Вердикт:** Для лабораторного стенда PL1 достаточен. В Roadmap v1.1 запланирован переход на PL2 с кастомными правилами исключений (снижение FP). *(Примечание: базовые правила WAF всё же ловят sqlmap по User-Agent и простой обфускации).*

## 5. Fail2Ban не интегрирован в Wazuh

**Симптом:** Fail2Ban успешно банит IP атакующего в `iptables` (правило `f2b-sshd`), но алерт об этом не появляется в Wazuh Dashboard.
**Причина:** В Wazuh нет нативного декодера для формата лога `/var/log/fail2ban.log`. Fail2Ban работает как независимый локальный слой защиты. Wazuh видит сами попытки SSH-логина (правило `5760`), но не видит команды бана от Fail2Ban.
**Вердикт:** Дублирование функциональности (Wazuh AR банит через iptables, F2B банит через iptables). В Roadmap v1.1 запланирована официальная интеграция.

## 6. UFW + Docker конфликт

**Симптом:** Порядок загрузки UFW и Docker приводит к тому, что правила `DOCKER-USER` не применяются, или UFW блокирует трафик контейнера WAF. Также использование `iptables -F` полностью ломает связи цепочек UFW и Docker.
**Решение:** В стенде используется `after.rules` для UFW + `ufw reload` + `docker restart`. Все команды снятия банов должны быть точечными (`iptables -D`), **никогда не использовать `iptables -F`** на хостах с Docker/UFW.

## 7. Ограничение детекта NULL-сканирования (VirtualBox)

**Симптом:** Пакеты NULL Scan (`hping3 -0`) отправляются с Kali, но Suricata и Wazuh их не видят.
**Причина:** Пакет с нулевыми TCP-флагами отбрасывается сетевым стеком ядра Linux (или виртуальным коммутатором VirtualBox) до того, как он попадет на интерфейс `enp0s8`, который прослушивает Suricata.
**Вердикт:** Ограничение виртуальной среды. В реальной сети пакеты доходят до IDS. (В Roadmap v1.1 запланировано удаление этого теста из скриптов).

## 8. Active Response и спуфинг IP

**Симптом:** При проведении DDoS-атак с подменой IP (`hping3 -a 10.0.0.x`) Active Response блокирует именно фейковый IP, а реальный IP Kali остается доступным.
**Причина:** Active Response работает на основе данных Suricata, которая видит IP-адрес из заголовка пакета (L3). При спуфинге блокируется ложный адрес. В проде для этого требуется uRPF (Unicast Reverse Path Forwarding) на пограничных маршрутизаторах.

## 9. IDOR (логические уязвимости)

**Симптом:** Атаки на IDOR (Insecure Direct Object References) не блокируются WAF (Coraza).
**Причина:** IDOR — это логическая уязвимость приложения (доступ к чужому объекту по прямому ID), а не сигнатура в запросе. WAF не умеет анализировать бизнес-логику приложения.
**Вердикт:** By design. Для защиты от IDOR требуются изменения в коде самого приложения (проверка прав доступа), а не WAF.

## 10. Дедупликация Telegram-бота (Alert Fatigue)

**Симптом:** WAF блокирует 7 OWASP-атак (SQLi x5, XSS, Cmdi, LFI), в Wazuh Dashboard появляется 7 алертов, но в Telegram приходит только 4-5 сообщений.
**Причина:** Бот использует функцию `is_spam` для защиты дежурного от усталости от алертов. Он склеивает одинаковые типы атак с одного IP-адреса в 5-минутное окно.
**Вердикт:** Это фича. В реальном SOC дежурный получает уникальные векторы атак, а полную историю (все пейлоады) смотрит в SIEM (Wazuh).
