# Hardening: Настройки безопасности

Этот документ описывает конфигурацию всех защитных механизмов лабораторного стенда. Каждый уровень (сеть, приложение, контейнер) настроен по принципу минимальных привилегий (Least Privilege) и эшелонированной защиты.

## 1. Периметр (iptables и UFW)

Настройка сети выполняется на двух уровнях: через стандартный `UFW` (для управления доступом) и через кастомные цепочки `iptables` (для защиты от DDoS и изоляции Docker).

### 1.1. Цепочка CUSTOM_DDOS
Скрипт `hosts/victim/network/08-iptables.sh` создает цепочку `CUSTOM_DDOS`, которая применяется первой в цепочке `INPUT`.

**Защита от флудов (Rate Limiting):**

| Вектор атаки | Модуль | Лимит | Burst (всплеск) |
|:---|:---|:---|:---|
| **SYN Flood** | `hashlimit` | 100 пакетов/сек | 200 |
| **UDP Flood** | `hashlimit` | 200 пакетов/сек | 400 |
| **ICMP Flood** | `hashlimit` | 10 пакетов/сек | 20 |
| **ACK/RST Flood**| `hashlimit` | 100 пакетов/сек | 200 |

**Блокировка аномалий (DROP):**
*   Пакеты с флагами `NULL` (нет флагов) и `XMAS` (все флаги).
*   Невалидные комбинации: `SYN+FIN`, `SYN+RST`, `PSH+ACK` (без ACK).
*   **LAND-атака:** пакеты, где Source IP совпадает с Destination IP.

### 1.2. Изоляция Docker (DOCKER-USER)
Скрипт `09-docker-user-hardening.sh` настраивает цепочку `DOCKER-USER`. Docker по умолчанию обходит правила UFW и `INPUT`, поэтому эта цепочка критически важна.
*   Разрешены только установленные соединения (`ESTABLISHED,RELATED`).
*   Разрешены входящие на порты `80` и `443`.
*   Разрешено проксирование от WAF-контейнера (`172.28.0.2`) к Apache на хосте (`172.28.0.1:8080`).
*   **Всё остальное — DROP.**

### 1.3. UFW (Uncomplicated Firewall)
Политика по умолчанию: `deny incoming`, `allow outgoing`.
Открыты только необходимые порты:
*   `22/tcp` (SSH)
*   `80/tcp` (HTTP, редирект на HTTPS)
*   `443/tcp` (HTTPS, WAF)
*   `8080/tcp` (ТОЛЬКО для IP `172.28.0.2`, т.е. для WAF-контейнера)

> ⚠️ **Важное правило:** Никогда не используйте `iptables -F` на этом хосте. Это удалит jump-правила UFW и Docker, оставив систему без сети. Баны снимаются только точечно: `iptables -D INPUT -s <IP> -j DROP`.

## 2. Защита веб-приложения (Nginx)

Nginx в Docker-контейнере (`coraza-waf`) выполняет роль обратного прокси и L7-файрвола.

### 2.1. Rate Limiting (Ограничение скорости)
*   **`limit_req`**: 20 запросов в секунду на IP, с `burst=30` (допускается всплеск до 30 запросов). При превышении Nginx отдает `429 Too Many Requests`.
*   **`limit_conn`**: Не более 20 одновременных соединений с одного IP. Защита от Slowloris и удержания соединений.

### 2.2. Таймауты (Защита от медленных атак)
*   `client_header_timeout 10s` (если клиент не прислал заголовки за 10 сек — разрыв).
*   `client_body_timeout 10s`.
*   `send_timeout 10s`.

### 2.3. Ограничение методов и заголовков
*   Разрешены только методы `GET`, `POST`, `HEAD`. Остальные (PUT, DELETE, TRACE) возвращают `405 Method Not Allowed`.
*   `client_max_body_size 10m` (защита от переполнения буфера большими файлами).
*   `server_tokens off` (скрытие версии Nginx в заголовках).

### 2.4. Security Headers
В ответы Nginx добавляются заголовки безопасности:
*   `X-Frame-Options: DENY` (защита от Clickjacking).
*   `X-Content-Type-Options: nosniff` (запрет MIME-sniffing).
*   `Strict-Transport-Security: max-age=31536000; includeSubDomains` (HSTS, принудительный HTTPS).

## 3. Изоляция Docker-контейнера

WAF (Coraza) запускается в изолированном контейнере.
*   **Сеть:** Выделенная сеть `waf-network` (`172.28.0.0/24`), фиксированный IP `172.28.0.2`. Это позволяет жестко прописать правила UFW и `DOCKER-USER`.
*   **Права:** Контейнер запускается с флагом `--group-add 2001` (группа `waf-logs`). Это дает ему права на запись логов в `/var/log/coraza`, не давая прав root на хосте.
*   **Монтирование:** Конфиги монтируются в режиме read-only (`:ro`), чтобы compromised-контейнер не мог изменить свои же правила.

## 4. Защита SSH (Fail2Ban)

Fail2Ban работает локально на Victim и защищает порт `22`.
*   **Jail:** `[sshd]`
*   **Мониторинг:** `/var/log/auth.log`
*   **Параметры:**
    *   `bantime = 1h` (бан на 1 час).
    *   `findtime = 10m` (окно анализа).
    *   `maxretry = 3` (3 неверных попытки до бана).
*   **Действие:** Вставка правила `DROP` в цепочку `f2b-sshd` (iptables).
*   *Примечание:* Интеграция Fail2Ban с Wazuh не настроена (см. Gap Analysis), но логи попыток входа (правило `5760`) Wazuh видит.

## 5. Оптимизация Suricata (Pass Rules)

Для предотвращения ложных срабатываний (False Positives) и защиты Wazuh Server от случайного бана, в Suricata добавлен файл `pass.rules`.

```text
pass ip 192.168.56.10 any <> any any (msg:"Whitelist Wazuh Server"; sid:1000000;)
pass ip any any <> 192.168.56.10 any (msg:"Whitelist Wazuh Server"; sid:1000001;)
```

Эти правила применяются **до** основных правил детектирования. Они заставляют IDS игнорировать весь трафик, связанный с сервером, даже если он похож на ACK Flood (что часто бывает при отправке больших объемов логов агентом).
